## Управление из другой программы

`--progress json` разделяет две аудитории, которые раньше делили один поток:

```
stdout   exactly one JSON object per line, nothing else, ever
stderr   the human log, unchanged and still worth reading
```

```
uv run openm74 --port COM3 --progress json --flash image.bin --yes
{"baud": 9600, "event": "stage", "ok": true, "stage": "handshake"}
{"addr": 12591104, "baud": 115200, "bytes": 843776, "estimate": 422, "event": "stage", "resume": false, "sectors": 206, "stage": "writing"}
{"addr": 12591104, "done": 1, "eta": 28, "event": "progress", "op": "write", "retries": 0, "skipped": false, "total": 206, "unit": "sectors"}
{"addr": 12644352, "detail": "no memory behind this address", "event": "problem", "fsr_op": 3, "fsr_prot": 0, "image_bytes": 4085, "kind": "unmapped", "known": "reserved by the device (XC2000 flash module 0, physical sector 15)"}
{"event": "result", "message": "every sector written was verified", "ok": true, "skipped": 0, "unmapped": 1, "unmapped_image_bytes": 4085, "what": "write", "written": 205}
```

Эти строки **сняты с настоящего прогона**, а не написаны от руки: предыдущая версия этого
раздела была написана вручную, объявлялась настоящей и врала про событие `problem` сразу
четырьмя способами — плохой подарок тому, кто пишет разбор. Обратите внимание:

* ключи выводятся **отсортированными** (`json.dumps(..., sort_keys=True)`), а адреса —
  целыми числами, а не шестнадцатеричными строками;
* события `problem` несут **`detail`**, а не `message` — `message` принадлежит `result`.
  Смешение этих двух и есть то, как словарь такого размера перестаёт быть контрактом;
* `problem` может нести дополнительные ключи (`known`, `fsr_op`, `fsr_prot`); считайте
  незнакомые ключи добавлением и не требуйте их наличия.

Четыре вида, и словарь намеренно крошечный, чтобы он мог стоять на месте: `stage` — грубая
веха, `progress` с `done`/`total`/`unit`, `problem` — переживаемое, о чём стоит сообщить, и
`result` — исход этапа, который может пройти или провалиться.

**Правило вердикта, которое важнее схемы:** операция удалась *тогда и только тогда*, когда
пришёл хотя бы один `result` и ни один из них не сказал `ok: false`. **Отсутствие
результатов — не успех**: это случай, когда прогон умер, не доделав ничего.

**Код возврата процесса согласован с этим правилом**: ноль только тогда, когда работа, о
которой просили, удалась. Раньше он был нулём при любом исходе, так что
`openm74 --flash img.bin --yes && echo ok` печатал `ok` над блоком, который только что
остался незаписанным, — это стоит знать, если у вас есть скрипт, написанный под старую
сборку.

Сделать это правильно удалось со второго захода, и второй стоит назвать, потому что в эту
ловушку легко попасть снова. `sys.exit(True)` выходит с **1**: `bool` — подкласс `int`, а
`sys.exit` передаёт целое напрямую как код возврата. То есть естественно выглядящий
`return ok` в конце ветки объявляет каждый успех неудачей, а каждую неудачу успехом — и на
каждом отдельном месте читается правильно. Теперь все ветки проходят через один нормализатор
(`exit_status`), а отображение закреплено тестом.

Всё это существует потому, что GUI раньше восстанавливал полосу прогресса регулярным
выражением по прозе и решал вопрос успеха поиском фразы в журнале: переформулировка одного
`print` молча ломала полосу, а успех, напечатанный *предыдущей* операцией, мог быть отнесён к
следующей, провалившейся. Флешеру, который умеет сказать «готово, проверено» о незавершённой
записи, нечего делать в поставке. Группа [18] тестов на фальшивом ЭБУ удерживает контракт на
месте.

## Сборка приложения

Один скрипт, на какой бы платформе вы ни были: второй сборщик — это способ добиться, чтобы
платформа, под которую на этой неделе никто не собирал, тихо перестала давать рабочий
артефакт.

```
uv sync
uv run python tools/build_exe.py
```

| Платформа | Что получается |
|---|---|
| Windows | `dist/openm74.exe` |
| macOS | `dist/openm74.app` и его `.zip`, с хешем |
| Linux | `dist/openm74` |

**На Debian и Ubuntu** дополнительно нужны два системных пакета, которые не являются
зависимостями Python и поэтому не входят в `uv sync`: `python3-tk` для интерфейса и
`libpython3-dev` — PyInstaller'у нужна *разделяемая* библиотека Python, которую эти
дистрибутивы пакуют отдельно от интерпретатора, и без неё однофайловая сборка кончается, не
начавшись. Скрипт сборки распознаёт именно этот отказ и называет нужный пакет.

Скрипт сборки запускает результат, прежде чем считать его собранным, и самопроверка проверяет
то, что может сломаться *только* внутри бандла: что собранные стадии доехали (без них
побайтная сверка с выводом ассемблера молча превращается в пустышку), что перечисление
последовательных портов ещё работает (на macOS pyserial обращается к IOKit через `ctypes`,
который упаковщик отслеживать явно отказывается), и что Tk вообще способен открыть окно.
Успешный прогон PyInstaller не говорит ни о чём из этого.

Ни одна из сборок **не подписана платной подписью.** Windows SmartScreen назовёт .exe
неизвестным издателем, а однофайловая упаковка иногда задевает эвристики антивирусов; macOS
откажется запускать .app при первом запуске, пока вы не сделаете правый клик → «Открыть».
Подпись стоит денег, которых этот проект не тратит. Сборки PyInstaller к тому же **не
воспроизводимы**, так что «проверьте пересборкой» — нечестная инструкция; именно поэтому
список зависимостей — это стандартная библиотека Python плюс pyserial, и собрать свою копию
занимает минуту.

Бандл macOS подписан ad-hoc (именно это позволяет ему запускаться на Apple Silicon вообще) и
объявляет минимальную версию macOS, вычитанную из собранного двоичного файла, а не угаданную:
без неё старый Mac не отказывает приложению вежливо, а умирает в динамическом компоновщике и
выглядит как испорченная загрузка.

## Тесты

```
uv run python tests/test_monitor_offline.py    # blob vs assembler, patch sites, gate, framing
uv run python tests/test_monitor_fakeecu.py    # end-to-end against a simulated ECU
uv run python tools/check_gui_platform.py      # the GUI's platform assumptions, on this OS
uv run python tools/build_stages.py            # the .bin files vs the .asm they came from
uv run python tools/check_docs_parity.py       # every number and identifier, English vs Russian
```

Симулированный ЭБУ говорит на настоящем протоколе, моделирует флеш так, как ведёт себя
кристалл (стирание читается как `0x00`, программирование только зажигает биты), и умеет
пачкать линию так, как это делает настоящее железо. Он ловил настоящие дефекты, которых не
поймали прогоны на живом блоке.

Проверка документации сравнивает то, что перевод не имеет права менять: числа, записанные
цифрами, шестнадцатеричные адреса, всё в обратных кавычках и цели ссылок. Прозу она читать не
умеет и не пытается. Каждое расхождение в документации, которое этот проект реально пережил,
было одним из этих четырёх — стоимость сектора, равная 2.05 с в одном месте и 2.64 в другом;
число зондов 48 против 16; английская справка, всё ещё обещавшая «около часа» там, где
русская говорила тринадцать минут. Человек, читавший любую половину отдельно, не поймал ни
одного.

Проверка платформы существует потому, что у GUI два способа сломаться на разных платформах, и
оба тихие: биты клавиш-модификаторов отличаются (Command приходит другим битом, чем Control,
так что обработчик только на Ctrl делает журнал некопируемым на macOS), а схема колодки
разложена в пикселях под шрифты, которые на каждой платформе свои. Ни то, ни другое не
вызывает исключения — рисунок просто становится неверным. Поэтому она синтезирует нажатия и
измеряет каждую строку относительно ячейки, в которую та должна поместиться.
