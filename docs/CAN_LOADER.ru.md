# CAN-загрузчик во flash: офлайн-разбор

Статус: анализ без записи на macOS в Ghidra 12.1.4. CAN-кадры не отправлялись,
операции с ЭБУ не выполнялись. Подробный дизассемблерный разбор охватывает представителей вариантов загрузчика,
дополнительно выполнено сравнение байтов других образов. Это не проверенная процедура
программирования или новый поддерживаемый транспорт.

## Образ и границы анализа

Образ: I444GI04, 851968 байт, размещён с `0xC00000`, SHA256
`166bbdd475930e5fc2f15035435505fc999e07d8a2d915595246f45fe0bff59b`.
Память загруженного проекта Ghidra независимо хеширована и совпала с файлом.
Это не прежний стендовый эталон из AGENTS.md; подменять им тот эталон нельзя.
Образы и полные листинги хранятся вне репозитория: дамп может содержать
идентификаторы донорского блока.

В исследованном загрузочном секторе есть инициализация CAN, стартовый обмен,
цикл команд и процедуры стирания/записи flash. Это подтверждает наличие
CAN-загрузчика во flash, отдельного от масочного ROM BSL, выбираемого выводами.
Это не доказывает возможность выгрузки полного образа или такое же поведение
других версий прошивки.

## Путь после сброса

| Адрес | Наблюдаемая инструкция или переход |
|---|---|
| `0xC00000` | Переход на `0xC002A2` |
| `0xC002A2` | Чтение `0xF0B2`, маска `0x3000`, сравнение с `0x3000` |
| Ветка равенства | Переход во вход приложения `0xC02000` |
| Ветка неравенства | Переход в инициализацию окружения загрузчика `0xC00D4A` |
| `0xC00D92` | Вызов входа загрузчика `0xC002BC` |
| `0xC0021A` | Запись `0x3000` в `0xF0B8` при инициализации загрузчика |
| `0xC002CE` | Вызов ограниченного стартового обмена `0xC002E4` |
| Обмен не состоялся | Выполнение `SRST` по адресу `0xC002DA` |
| Успешный обмен | Вход в цикл команд `0xC0059C` |

Системное руководство XC2000 определяет `0xF0B2` как `RSTSTAT0`; проверяемые
биты — `CPU[13:12]`. Значение `11` означает сброс приложения по запросу сброса CPU.
`0xF0B8` — это `RSTCON0`; запись `0x3000` выбирает такой тип сброса для `SRST`.
Статическая интерпретация: при старте есть возможность обмена, а при его неудаче
происходит сброс с переходом в приложение. Это не проверка внешнего вывода
программирования. Предполагается, что исполнение дошло до вектора сброса во flash;
выбор ROM BSL — отдельное решение на более ранней стадии.

Инициализация приложения загружает адрес `RSTCON0` по `0xC0247C`, добавляет через OR
`0x3000` и сохраняет его по `0xC02486`. Функция сброса и выбранные вызывающие ветви
исследованы ниже; программный путь входа в резидентный загрузчик пока не установлен.

### Путь сброса приложения: один точный образ

Этот анализ относится к указанному выше образу I444GI04, а не ко всем совпадениям
загрузочного префикса. Байты приложения могут различаться при одинаковом загрузочном
секторе. Функция сброса начинается по `0xC0D572`: копирует `r12` в `r1`, сравнивает
младший байт с `0x90` и при неравенстве переходит к хвосту по `0xC0D6B6`. Этот хвост —
`NOP`, затем `SRST` по `0xC0D6B8`. Равенство вместо этого запускает подготовку по
`0xC0D57C`, с записями RAM/периферии и вызовами функций перед тем же хвостом сброса.
Значение — аргумент функции, а не установленная команда на шине. Ниже дан ограниченный
статический обзор функций; их транзитивные эффекты и все предшествующие переходы
состояния полностью не проверены.

Короткий путь неравенства не меняет настройку сброса. Если наблюдаемая настройка
приложения сохраняется, его сброс приложения CPU выберет ветку приложения в развилке
сброса flash, а не откроет заново стартовый обмен CAN. Этот условный результат объясняет,
почему обнаружение функции сброса само по себе не устанавливает программный вход в
загрузчик. Он не исключает другой путь изменения настройки сброса, иной источник
сброса, прямой переход или дополнительную логику неисследованных вызываемых функций.

Поиск в сырых байтах с выравниванием находит семь кандидатов прямых `CALLS` этой функции,
каждый декодирован как такой вызов. Выбранные окружающие ветви дают следующие локальные
условия; это не полная проверка достижимости, авторизации или транспорта:

| Места вызова | Локальные условия буфера и аргумент |
|---|---|
| `0xC507D2`, `0xC5D208`, `0xC5D28A` | Байт по `0xDE74` равен `0x11`, байт по `0xDE7B` равен `0x01`; аргумент берётся из `0xDE64` |
| `0xC6050E`, `0xC6AA1A`, `0xC6AAAC`, `0xC6AB6C` | Байт по `0xDEF8` равен `0x11`, байт по `0xDEF9` равен `0x01`; аргумент берётся из `0xDEE9`, причём `0x91` на этих ветвях исключён |

Источники пути сброса и программный путь CAN для второго разборщика определены ниже;
первый физический транспорт и полные условия диагностической сессии/доступа не установлены. Нельзя превращать таблицу в запрос
CAN или считать, что стандартная служба с похожими значениями реализует этот путь.
Поиск сырых вызовов не находит косвенные вызовы, ближние переходы или все возможные входы.
Поиск выровненного опкода `SRST` во всём образе находит два вхождения по `0xC002DA` и
`0xC0D6B8`; наличие опкода не доказывает достижимости исполнения или отсутствия
других механизмов сброса.

Часть `tools/ghidra/CheckApplicationReset.java` для префикса сброса исполняет только короткий
префикс регистровых операций/ветвления в новых экземплярах эмулятора Ghidra. Все 256 значений младшего байта
проверены со старшими байтами `0x00`, `0x01`, `0x80`, `0xFF`: 1024 случая, из них 4
достигают подготовки, а 1020 — `NOP` хвоста сброса. Исполнение останавливается перед
этой инструкцией либо на входе подготовки; `SRST`, вызываемые функции подготовки,
сброс CPU и эффекты периферии не эмулируются. Userop декодера для `NOP` вне этой проверки.
Отдельная обвязка проверяет точный хеш образа, хеш загруженной памяти и маркер успеха;
одного кода завершения Ghidra недостаточно.
[Отчёт](data/application-reset.json) содержит метаданные и адреса, а не байты прошивки.

```
python tools/check_application_reset.py IMAGE.bin --report reset-evidence.json
```

Инструмент отвергает другие образы, а не переносит адреса этого приложения на всё
семейство. Приведённые ниже разборщики и статическое обследование функций добавляют
локальные свидетельства; ни найденные места вызовов, ни ограниченная проверка ветвления
не устанавливают работающий программный вход в CAN-загрузчик.

### Признак состояния подготовки и источник параметра

Ветка подготовки записывает `0x2222` по `0xC0D672` в смещение `0x2406` с помощью
`EXTP 0x380`, то есть по физическому адресу `0xE02406`. Потребитель по `0xC033B4` читает
ту же ячейку, сравнивает с `0x55AA` и при несовпадении переходит на `0xC03488`. Другие
исследованные пути приложения записывают `0x55AA` по `0xC06114` и обнуляют ячейку по
`0xC08232`. Поэтому значение подготовки не проходит эту проверку валидности состояния
приложения, если сохраняется до чтения. Сохранение RAM и промежуточные записи через
сброс не проверены. Описанная выше развилка сброса flash читает статус сброса, а не эту
ячейку; считать значение доказанным флагом входа в загрузчик оснований нет.

Источники именно пути сброса определены в разделе разборщиков ниже. Несколько служб
пишут в общие ячейки аргумента; совпадение назначения само по себе не связывает источник
с конкретным вызовом сброса. Первый физический транспорт остаётся неустановленным;
программный путь приёма CAN второго разборщика установлен ниже при допущениях модели.

Та же воспроизводимая проверка теперь статически следует прямым ветвям и продолжениям
в пяти функциях подготовки. Она не входит в вызываемые ими функции и не исполняет
подготовку. Учитываются все условные ветви независимо от фактических аргументов
подготовки; это ограниченное обследование CFG, а не наблюдаемые пути работающего ЭБУ:

| Вход | Декодированные начала инструкций | Места прямых вызовов | Различные прямо вызываемые функции |
|---|---|---|---|
| `0xC1055E` | 2811 | 408 | 10 |
| `0xC12F10` | 359 | 33 | 8 |
| `0xC4577C` | 241 | 16 | 5 |
| `0xC45720` | 38 | 4 | 1 |
| `0xC10000` | 22 | 1 | 1 |

Функция по `0xC10000` содержит вложенные счётные циклы, инструкции `NOP` и вызов
`0xC0272C`, где исследованная последовательность обслуживает watchdog через `SRVWDT`
и возвращается. Это поддерживает роль задержки/обслуживания watchdog, но не устанавливает
миллисекунды. Остальные функции существенно обрабатывают RAM и делают дальнейшие
вызовы; транзитивные эффекты периферии этим обследованием не установлены. Неразрешённый
косвенный поток управления, ошибка декодирования или выход за исследованное окно функции
завершают проверку ошибкой, а не молча обрезают её. Отчёт перечисляет прямо вызываемые
функции, исключённые из каждого обхода. Он не доказывает отсутствия записи регистра
сброса в более широком графе вызовов.


Ограниченная проверка подготовки ниже устанавливает непосредственные аргументы вызовов
и отдельные начальные участки функций. Полный допуск запроса и транзитивные эффекты ещё
требуют разбора; ни одна из этих проверок не устанавливает программный вход в загрузчик.

### Подготовка с фактическими аргументами вызовов

`tools/check_reset_preparation.py` исполняет верхний уровень ветки `0x90` с синтетической
RAM и исследованным отображением DPP приложения. Вызовы функций фиксируются и пропускаются,
результаты `r4` подставляются; исполнение останавливается перед `NOP` хвоста сброса
в `0xC0D6B6`. Шесть сценариев покрывают снятый/установленный флаг ветвления и результаты
0, 3 и `0xFFFF`; ещё один проверяет переход аргумента `0x01` к хвосту без вызовов
подготовки. Пропущенные вызовы не означают завершения функций или выполнения сброса.

Ветвление в `0xC0D682` читает бит 4 ячейки RAM `0xFD1E`. Один источник проверен
ниже; физический смысл и последующие изменения флага остаются неизвестными. Зафиксированы следующие последовательности:

| Флаг | Порядок вызовов и явные аргументы |
|---|---|
| Снят | `0xC4577C` с `r12=1`; `0xC10000` с `r12=0x64`; `0xC45720` с `r12=1`; `0xC10000` с `r12=0x0A` |
| Установлен | `0xC1055E` с `r12=1`, `r13=0x569C`; `0xC12F10` с `r12=1`, `r13=0x5864`; `0xC10000` с `r12=0x0A` |

Инструкции верхнего уровня не проверяют `r4` между этими вызовами и хвостом сброса;
подстановка локальной ошибки не останавливает модельный путь. Вызываемая функция всё
ещё может зависнуть, сбросить блок, изменить память или иначе не вернуться — эти эффекты
не моделируются. Верхний уровень записывает маркер и другое состояние, включая ноль
в `0x204010`. Отслеживание записей памяти видит запись маркера, но не видит записи
в `0xF0B8` — `0xF0BB` в этих сценариях верхнего уровня. Это не доказательство отсутствия
записей в пропущенных функциях или прерываниях.

Ещё четыре сценария входят в обе функции последовательной ветки с фактическими аргументами
и останавливаются перед первыми вложенными вызовами: `0xC120DC` и `0xC1317E`.
Ранний вызов чтения второй функции в `0xC12F70` относится к режиму 2 и не достигается
проверенным начальным участком режима 1. Независимый разбор дескрипторов и исполненное
копирование дают:

| Дескриптор | Записей данных | Скопировано байт | Байт в цикле контрольной суммы | Сохранённый хвост |
|---|---|---|---|---|
| `0xC8169C` | 52 | 315 | 320 | 5 |
| `0xC81864` | 58 | 514 | 528 | 14 |

При начальном заполнении рабочих буферов нулём или `0xA5` хвосты буферов в `0xB22C`
и `0xB00C` остаются неизменными после упаковки, а их байты участвуют в аддитивной
контрольной сумме. Первые упакованные байты также отражают слова, установленные реальными
инструкциями верхнего уровня. Значит, исследованные функции сами по себе не делают
все обрабатываемые байты независимыми от прежнего содержимого рабочего буфера. Хвост
может быть резервом или инициализироваться в другом месте; это чувствительность модели,
а не наблюдаемый отказ ЭБУ или доказательство неопределённой RAM при запуске.

Ещё 16 сценариев исполняют источник флага от `0xC031FC` до `0xC0320C`,
останавливаясь перед следующим вызовом. Флаг устанавливается только при ненулевом
младшем байте результата `0xC1034E` и нулевом логическом конфигурационном байте
`0x4A52`. При исследованном отображении DPP этот байт находится в `0xC80A52` и
равен 1 в точном образе: этот источник поэтому снимает флаг, выбирая другую цепочку
подготовки, если флаг не изменится до подготовки сброса. Тесты покрывают оба начальных
значения флага, характерные результаты, включая `0x0100`, и исходный байт против
синтетического нулевого байта в памяти эмулятора. Они не исполняют `0xC1034E`, всю
инициализацию или последующие записи флага. Наличие последовательного пути само по
себе не устанавливает его штатный выбор на этой плате/образе.

Все 27 сценариев прошли. [Отчёт](data/reset-preparation.json) фиксирует хеши точного
образа, скриптов и найденного декодера. RAM синтетическая, стартовая инициализация не
исполняется, остальные функции верхнего уровня пропускаются; численные и последовательные
функции за границами начальных участков не вызываются. Полная транзакция сохранения,
поведение периферии и программный вход в загрузчик не подтверждены.

### Подготовка при снятом флаге: упаковка и границы менеджера хранения

`tools/check_clear_flag_preparation.py` проверяет `0xC4577C` и `0xC45720` с
`r12=1` — аргументом ветки сброса при снятом флаге. В выбранную дескрипторами RAM
помещаются сгенерированные байты, исполняются упаковка и управляющие инструкции;
инициализация, постановка и статус менеджера хранения явно моделируются. Эти операции
менеджера и полная транзакция от верхнего уровня до flash не исполняются. Свидетельства
относятся только к тому же точному stock-образу.

`0xC4577C` вызывает инициализацию слотов 4, 5 и 6, упаковывает дескриптор
`0xC8169C` в три буфера, затем ставит задачи этим слотам с режимом 1. `0xC45720`
исполняет `0xC455FA` для дескрипторов `0xC8132C` и `0xC8150C`, используя слоты 0 и 1.
Общий буфер используется последовательно. Каждая модельная инициализация заполняет
буфер значением `0xA5`; это заменяет реальное поведение инициализации/чтения, а не
утверждает значение стёртой памяти.

| Слоты | Начала буферов RAM | Скопировано данных | Байт в буфере | Байт перед данными | Сохранено байт после данных |
|---|---|---|---|---|---|
| 4, 5, 6 | `0xE030A4`, `0xE03DA4`, `0xE03BA4` | 315 | 512 | 12 | 185 |
| 0 | `0xE032A4` | 1955 | 2048 | 12 | 81 |
| 1 | `0xE032A4` | 1886 | 2048 | 12 | 150 |

Тест сравнивает каждый скопированный байт со сгенерированным источником по дескрипторам
и проверяет сохранение исходного заполнения хвоста. Это устанавливает границы упаковки,
а не смысл полей или полный формат заголовка постоянного хранения. Скопированные данные
и сохранённый хвост нельзя отождествлять с полной резервной копией.

Восемь сценариев варьируют подставленный результат постановки и конечный статус;
ещё два входят в реальную ветку неготовности `0xC4491A` при нулевом управляющем байте
`0xC4E0` и неизменном нулевом статусе `0xC4E2`. Обе функции верхнего уровня проходят
свои слоты и возвращают локальное значение 2 в этих сценариях. Результат постановки
там не проверяется, а конечный статус 3 обрабатывается так же, как 0. Значение 2
поэтому не является независимым свидетельством сохранения содержимого. Это контрпримеры
вызывающего кода с пропущенной инициализацией, а не наблюдаемый отказ реального менеджера
или полная спецификация его статусов.

`0xC44A20` только читает `0xC4E2`. Два участка с удерживаемым статусом 1 остаются
в циклах ожидания с вызовами watchdog без локального лимита попыток. Чтение статуса не
продвигает операцию хранения; планирование и завершение других путей исполнения остаются
вне модели. Прошедшее время или зависание оборудования не установлены.

Исследованные записи слотов в `0xC82A4A` с шагом 24 задают слотам 4, 5 и 6
относительные начала `0x8000`, `0xA000`, `0xC000`, размер записи 512 и количество 16.
Три отдельных теста входят в нижний API `0xC4505A` с этими смещениями и длиной 512
и останавливаются перед вызовом обработчика в `0xC450E0`. Сохранённый адрес задачи
становится соответственно `0xCC8000`, `0xCCA000`, `0xCCC000`. Ещё два отказа покрывают
неготовность и интервал вне допустимых границ. Записи командных портов происходят только
в RAM эмулятора; сквозная передача аргументов менеджером и эффекты асинхронного обработчика
и flash не исполняются. Это даёт конкретную гипотезу адресов хранения в хвосте,
исключённом CAN-интерфейсом, и подкрепляет требование отдельно сохранять этот хвост.

Все 17 сценариев прошли. [Метаданные](data/clear-flag-preparation.json) содержат хеши
образа, скрипта, унаследованного скрипта подготовки, адаптации адресов и найденного декодера.
Вызовы watchdog считаются и пропускаются, состояния RAM/контроллера синтетические;
сброс, IRQ и операции устройства не выполняются. Переходы менеджера проверены отдельно ниже.


### Переходы менеджера хранения

`tools/check_storage_manager.py` добавляет 22 сценария p-code точного образа с синтетической RAM.
Девять входят в `0xC44A26` в состоянии 1, исполняют подготовку аргументов и заменяют вызов
`0xC44EE4` результатами 0–7 или 65535. До этой границы доходят смещение `0x8000`,
страница источника `0x380`, смещение источника `0x30A4` и длина 512 на стеке.
Каждый внедрённый результат оставляет состояние менеджера `0xC5E4` равным 2, а общий
статус `0xC4E2` равным 1: этот переход не проверяет результат нижнего вызова.

Восемь отдельных входов в состоянии 2, по одному на слот, обновляют индекс выбранной
записи, очищают её байтовый флаг, состояние менеджера и общий статус. Тесты явно вызывают
менеджер и не устанавливают, когда прошивка планирует такой вызов. Пять сценариев исполняют
нижнее завершение `0xC453AC` с незаданным callback: переданные результаты 0/1/2/3/5
попадают в `0xC616`, а `0xC614` и `0xC624` очищаются. Эта нижняя ячейка результата
отличается от общего статуса, который читает функция подготовки сброса. Регистрация и маршрутизация callback проверены отдельно ниже; сами эти 22 сценария
такую связь не устанавливают.

Статический просмотр инструкций также отделяет прежний API `0xC4505A` от записи:
его обработчик `0xC450E8` копирует байты flash в RAM. Менеджер в состоянии 1 вызывает
`0xC44EE4`, чей декодированный путь проверяет цель и достигает `0xC45426`; программирование
и продвижение через прерывания эти тесты не исполняют. Адресные префиксы подтверждают
отображение адресов, а не завершённую запись. [Метаданные](data/storage-manager.json)
содержат хеши образа, скрипта, унаследованного скрипта подготовки, адаптации адресов и декодера.
Планировщик, IRQ, физика flash, сброс и операции устройства не моделируются. Ни локальный
возврат, ни очищенный общий статус сами по себе не доказывают сохранение.


### Зарегистрированные callback и завершение страницы

`tools/check_storage_callbacks.py` исполняет ещё 35 сценариев p-code точного образа. Один
начинается в `0xC0243E`, исполняет подготовку аргументов и инициализатор `0xC44D9E`,
останавливается в `0xC02452`. Он регистрирует callback успеха `0xC44A26` в
`0xC610`/`0xC612` и ошибки `0xC44A7C` в `0xC618`/`0xC61A` с синтетическими
начальными RAM/регистрами периферии. Десять сценариев исполняют нижнее завершение
`0xC453AC` с результатами 1/2/3/4/6 в состояниях менеджера 1/2. Callback ошибки
очищает состояние менеджера и переводит эти состояния в общий статус 2/3 соответственно;
нижний результат остаётся в `0xC616`.

Восемь сценариев входят в продолжение страницы `0xC4520C` с длиной 128, сгенерированной
страницей в `0xCC8000` и соответствующей исходной RAM. Проверяются совпадение страницы
и однобайтовые несовпадения по смещениям 0/63/127, каждое со сброшенным/установленным
битом 11 статуса `0xFFFF0A`. Реальный код сравнивает 32 четырёхбайтовых слова:
несовпадение даёт нижний результат 4, иначе установленный бит даёт результат 2.
Оба пути вызывают callback ошибки, сохраняют выбранный индекс записи и задают общий
статус 3. Совпадение при сброшенном бите очищает нижний статус и вызывает успех:
менеджер в состоянии 2 продвигает выбранный индекс и очищает общий статус. Подставленные
байты flash представляют снимок после операции, а не исполненную команду программирования
или физическую проверку чтением.

Все сценарии callback заменяют диспетчер дальнего возврата `0xC4FFEC` явным переходом
по загруженному прошивкой указателю; инструкции самих callback исполняются. Это не
эмуляция системного стека/прерываний. Ещё 16 сценариев исполняют входной фильтр
`0xC4554A`, начиная после инструкции watchdog: продолжение допускается только при
установленном бите 15 `0xFFFF04`, активном состоянии 1 и нижнем статусе 5. Режим 2
выбирает `0xC45188`; режим 1 — `0xC4520C`. Тесты останавливаются перед выбранным
вызовом. Декодированная обёртка прерывания `0xC4559A` вызывает этот обработчик и
заканчивается `RETI`; доставка прерывания, реальные эффекты регистров и время не
проверены. [Метаданные](data/storage-callbacks.json) содержат хеши образа, скрипта,
унаследованного скрипта подготовки, адаптации адресов и декодера.

Зарегистрированные callback объясняют, как успешное продолжение или ошибка продвигают
менеджер без участия опроса статуса. Это свидетельство условного программного пути,
а не продемонстрированное сохранение на ЭБУ. Сквозная последовательность и немедленные
отказы проверены ниже; физическая семантика команд/статусов остаётся непроверенной.
CAN-запись и аппаратные тесты не включены.


### Сквозное стирание/программирование и немедленный отказ

`tools/check_storage_sequence.py` добавляет 19 сценариев точного образа. Десять исполняют
реальную постановку `0xC4491A` с режимом 1 для слотов 0/1/4/5/6, каждый при обычном
переходе записи и при обороте индекса. Размеры слотов — 2048/2048/512/512/512 байт.
Исходная RAM сгенерирована; реальные инструкции контрольной суммы/заголовка и выбора
адреса исполняются. Скрипт отдельно представляет массив flash: записи командных портов
остаются командами, а не сохраняемыми байтами массива. Эффект стирания подставляет нули;
эффект программирования устанавливает 64 слова, реально загруженные `0xC45426`. Это
явные синтетические эффекты периферии, а не проверенный контроллер flash. Watchdog
пропускается, продолжения вызываются явно, диспетчер косвенных callback использует ту же
адаптацию, что предыдущий тест.

Сквозной путь: постановка -> продолжение стирания `0xC45188` -> проход нулевых страниц
через `0xC453D0`/`0xC45426` -> callback успеха при состоянии менеджера 1 -> проход
страниц данных через `0xC44EE4`/`0xC45426`/`0xC4520C` -> callback успеха в состоянии
2. Для этих длин шаг стирания равен 128 байтам; страница данных также равна 128 байтам.
Модель проверяет порядок всех целей, загрузку нулей, два callback успеха, выбранный индекс
записи и итоговый синтетический массив относительно обновлённой исходной RAM. За все фазы
требуются 3 вызова продолжения на страницу; измеренного времени это не задаёт. Ещё два
сквозных сценария повреждают первую страницу данных слота 4 или последнюю страницу данных
слота 0 после синтетического эффекта программирования. Реальное сравнение даёт нижний
результат 4/общий статус 3, останавливает продвижение и сохраняет прежний индекс записи.
Повторная попытка или восстановление прерванной записи не установлены.

Семь отдельных сценариев входят в реальный менеджер в состоянии 1 с заданными отказами,
без предшествующей фазы стирания. Проверки нижней неготовности, невыровненной цели,
неверной длины, нулевого источника и уже активной операции возвращают соответственно
1/6/7/5/4. Callback и новая команда отсутствуют, но менеджер всё равно записывает
состояние 2 и сохраняет общий статус 1. При начальном нижнем статусе 0 последующий
вызов обработчика не меняет это состояние; это ограниченный программный пример, а не
продемонстрированное зависание устройства или доказательство, что реальный путь сброса
может передать такие неверные аргументы. Ещё два сценария подставляют непустую цель или
установленный бит 11 `0xFFFF0A`: синхронные callback ошибки задают общий статус 2 и
очищают состояние менеджера, после чего возвращающийся менеджер перезаписывает своё
состояние значением 2. Нижние результаты остаются 1/2. Тесты показывают локальный порядок
и непроверенные результаты постановки, а не частоту или достижимость этих состояний
на оборудовании.

Все 19 сценариев прошли. [Метаданные](data/storage-sequence.json) содержат хеши образа,
скрипта, унаследованного скрипта подготовки, адаптации адресов и декодера. Физический статус
flash, реальные моменты прерываний, потеря питания, выбор восстановления и сохранность после
сброса остаются открытыми. Проверка записей и локального выбора восстановления приведена
ниже; сама эта последовательность не устанавливает атомарность сохранения всех слотов.


### Проверка записей и локальный выбор восстановления

`tools/check_storage_recovery.py` исполняет 46 сценариев точного образа. Он входит
напрямую в селектор `0xC44AA0` с исследованным дескриптором слота и указателем выходного
индекса. Реальные сканирование заголовков, чтение полной записи `0xC44BC0`, нижний API
чтения `0xC4505A`/`0xC450E8` и функция суммы `0xC44C50` исполняются на сгенерированных
записях flash. Регистры периферии представлены постоянно готовой RAM, callback не заданы.
Полный запуск, проверки геометрии инициализатором, значения по умолчанию, сброс и операции
flash не исполняются.

Девять сценариев для каждого слота 0/1/4/5/6 покрывают: пустую область; одну корректную
копию; новую копию с неверным маркером, суммой или неполной записью; равные счётчики;
счётчики `0xFFFFFFFF` и `0x00000000`; отсутствие корректной полной копии при правдоподобном
заголовке; обычную новую корректную копию. Сгенерированная запись имеет заголовок из
12 байт: маркер по +0, 32-битный счётчик по +4 и сумму по +8. Сумма складывает все
четырёхбайтовые слова по модулю `0x100000000`, исключая собственное поле. Это локальные
поля проверки, а не криптографическая целостность или установленная межслотовая транзакция.

Выбранные содержимое RAM и индекс соответствуют новой корректной копии в обычном случае;
неверный маркер/сумма/неполная новая запись приводят к выбору старой корректной копии.
Пустая область/отсутствие корректной записи дают возврат 2; прямой тест не исполняет
восстановление значений по умолчанию вызывающей функцией. При равных счётчиках по индексам
1/2 с разными сгенерированными данными выигрывает индекс 2. Если у прежней копии счётчик
`0xFFFFFFFF`, а у последующей — `0x00000000`, селектор выбирает прежнюю: в проверенной
паре сравнение не учитывает оборот счётчика при определении свежести. Это синтетическая
граница, а не наблюдавшийся отказ за срок службы или полный разбор переполнения при запуске.

Ещё один сценарий задаёт корректные старые записи всем пяти слотам, корректные новые —
слотам 0/1, а неполные новые — слотам 4/5/6. Независимые вызовы селектора выбирают
счётчики 18 для первой пары и 17 для второй группы. Это показывает, что данный селектор
может вернуть смешанные локальные счётчики записей; это не доказывает, что счётчики задают
общий момент сохранения или что всё приложение принимает такое сочетание после сброса.
Общая проверка согласованности здесь не исполняется.

Все 46 сценариев прошли. [Метаданные](data/storage-recovery.json) содержат хеши образа,
скрипта, унаследованного скрипта подготовки, адаптации адресов и декодера. Остаются вопросы
полного допуска при запуске и согласованности за пределами этого селектора. Инициализатор
и вызывающая функция трёх копий проверены ниже. Поведение прерванной записи на реальной
flash и сохранность по-прежнему требуют стендовых свидетельств.


### Флаги инициализатора и восстановление трёх копий

`tools/check_storage_initialization.py` исполняет 20 сценариев точного образа: слоты
0/1/4/5/6 с пустой областью, корректной копией, неверной новой копией при корректной
старой или без корректной полной копии. Исполняются реальные инициализатор `0xC447FE`,
проверки геометрии, селектор, чтение и сумма. Арифметическая функция `0xC5EA16` проходит
короткую ветку с фактическими аргументами 60000/15000; проверенное частное равно 4.
Другие её арифметические ветки этим не покрываются. Диспетчер дальнего callback заменён
явно; регистры периферии представлены постоянно готовой RAM. Полный запуск, сброс и
эффект стирания/программирования не моделируются.

Пригодная запись даёт результат инициализатора 0 и сохраняет выбранное содержимое.
Если пригодной записи нет, вызывается `0xC44CA4`: он записывает маркер дескриптора,
очищает счётчик и байты от +12 до конца, но сохраняет поле суммы по +8. Инициализатор
обнуляет выбранный индекс, записывает результат слота 2, вызывает callback дескриптора
и возвращает 10. При этом менеджер помечается готовым. Пять callback выставляют
исследованные биты: `0xFD50` бит 11, `0xFD12` бит 6, `0xFD40` бит 11, `0xFD00` бит 5
и `0xFD08` бит 10 соответственно. Они выставляют флаги, а не загружают прикладные значения
по умолчанию и не сохраняют подготовленную RAM во flash. [Метаданные](data/storage-initialization.json)
содержат хеши обоих унаследованных скриптов, образа, скрипта, адаптации адресов и декодера.

`tools/check_storage_consensus.py` добавляет 48 сценариев вокруг `0xC4577C(2)` —
пары к ранее проверенному вызову сохранения. Сорок сценариев матрицы сочетают все маски
пригодности слотов 4/5/6 с пятью вариантами равенства: все равны, каждая возможная
совпавшая пара или все различаются. Они заменяют инициализацию отдельных слотов и задают
её флаги непригодности. Пять сквозных сценариев исполняют реальные инициализаторы и чтение
сгенерированных записей flash. Реальный вызывающий код сравнивает байты от +12 до +511,
исключая заголовки. Он предпочитает совпавшую пригодную пару; если её нет, использует
первую пригодную копию в порядке слотов 4/5/6. Затем распределяет 315 байт в прикладную
RAM по дескриптору. Ветки выбора и итоговые байты RAM проверяются независимо. Это
политика восстановления трёх копий, а не сравнение их локальных счётчиков записей или
общая транзакция сохранения.

Ещё один сквозной сценарий оставляет эти 315 прикладных байт одинаковыми во всех копиях,
но меняет оставшиеся 185 байт так, что во всём сравниваемом диапазоне совпадают только
слоты 5/6. Вызывающая функция выбирает слот 5. Следовательно, сравнение захватывает
хвост вне распределяемых 315 байт; смысл его полей/резервных байтов остаётся неизвестным.
Равенство локальных счётчиков для этого сравнения данных не требуется. Автоматическое
исправление flash не исполняется.

При непригодности всех трёх копий реальный вызывающий код исполняет `0xC08566`, а не
распределяет обнулённую запись. Обработчик выставляет `0xFD72` бит 2 и загружает выбранные
параметры ROM, нулевые поля и байтовые сигнальные значения в прикладную RAM. Два прямых
сценария покрывают значения конфигурационного байта `0xC80B96` 0/1, причём последний
подставлен в память эмулятора: группа из восьми байтовых полей становится соответственно
`0xFF` или `0x00`. Проверены и другие выбранные загрузки ROM, константы и обновление
битовой маски. Это исполнение локального обработчика значений по умолчанию, а не
доказательство безопасности каждого поля как заводской конфигурации любого ЭБУ.

Скрипт также проверяет соседние декодированные вызовы около `0xC0326C`: режим 2
передаётся в `0xC4577C`, затем режим 2 — в `0xC45720`. Допуск в эту ветку или полный
запуск не исполняется. [Метаданные](data/storage-consensus.json) содержат хеши образа,
скрипта, унаследованных скриптов восстановления/подготовки, адаптации адресов и декодера.
Неизвестные вызовы, неинициализированное чтение, исчерпание бюджета инструкций и ошибки
скрипта Ghidra приводят к отказу проверок.

Таким образом, локальное восстановление содержит реальное сравнение копий слотов 4/5/6;
пример смешанных счётчиков независимого селектора не является полным восстановлением
приложения. Другие группы и ограниченный участок запуска проверены ниже; полный допуск
при запуске остаётся вне модели. Эта работа не устанавливает атомарность сохранения всех
групп или поведение прерванной записи на реальной flash. CAN-запись и аппаратные операции
не включены.


### Другие группы и участок восстановления при запуске

`tools/check_storage_other_groups.py` добавляет 77 сценариев точного образа со сгенерированными
записями, реальными инструкциями инициализации/чтения/суммы/распределения и постоянно готовыми
RAM-регистрами. Косвенный вызов callback задан явно; последовательные транзакции, сброс,
эффект стирания/программирования, доставка прерываний и полный запуск приложения не моделируются.

| Слоты | Вход восстановления | Проверенная политика | Распределяемые байты |
|---|---|---|---|
| 0/1 | `0xC45720(2)` -> `0xC455FA(2)` | Отдельные дескрипторы и записи | 1955/1886 |
| 2/3 | `0xC459FA(2)` | Приоритет 2, переход к пригодной 3; отдельный общий флаг | 88 |
| 4/5/6 | `0xC4577C(2)` | Совпавшая пригодная пара, иначе первая пригодная копия; проверено выше | 315 |
| 7 | `0xC45C7E(2)` | Одно поле, прикладное значение по умолчанию при непригодности | 1 |

Восемь сценариев дескрипторов слотов 0/1 покрывают пустую область, корректную запись,
неверную новую при корректной старой и отсутствие корректной полной записи. Реальные
функции распределяют выбранные данные либо обнулённую полезную часть, подготовленную
инициализатором при отсутствии пригодной записи. В этих сценариях чтения они возвращают
0. Ещё четыре сценария исполняют внешнюю обёртку для всех масок пригодности:
`0xC45720(2)` ожидает возврат 1 от каждой функции чтения и поэтому возвращает 6 даже
при корректном восстановлении сгенерированных данных. Это локальное несоответствие кодов
возврата, а не свидетельство отказа восстановления или отклонения данных всем запуском.

Шестнадцать сценариев пары покрывают все маски пригодности и оба значения сгенерированного
флага в каждой записи. Пригодный слот 2 всегда задаёт распределяемые 88 байт независимо
от счётчика/данных слота 3; пригодный слот 3 заменяет его только при непригодности слота
2. Если оба непригодны, распределяется подготовленная нулевая полезная часть слота 2.
Отдельно бит 0 `0xFDE2` выставляется, когда хотя бы одна пригодная копия содержит байт
1 по смещению полезной части 86, полученному из исследованного поля ROM. Поэтому этот
флаг может отражать слот 3, а распределённые данные — слот 2. Тесты не присваивают флагу
название какой-либо функции ЭБУ.

Шесть сценариев слота 7 покрывают значения 0/1/`0xA5`, пустую область, неверную сумму
и переход к старой корректной копии. Его дескриптор переносит один байт в `0xE016B4`.
При непригодности реальный обработчик `0xC086EE` подставляет `0xFF`. Вызывающие функции
пары и одиночного поля возвращают 0 в этих сценариях чтения; сам локальный возврат не
является заключением о пригодности записи.

Три сквозных сценария входят в `0xC03210` при сброшенном бите 4 `0xFD1E` с полностью
пустыми, полностью корректными или смешанными по пригодности записями. Они останавливаются
перед вызовом watchdog в `0xC0327E`. Реальный порядок вызова групп: `0xC459FA`,
`0xC4577C`, `0xC45720`, `0xC45C7E`, все с режимом 2; порядок инициализации слотов —
2/3/4/5/6/0/1/7. Каждый сценарий проходит возврат 6 обёртки и переходит к следующей
функции: в этом участке результат не проверяется. Проверено итоговое одиночное поле;
конфигурация сброса остаётся прежней. Это исполнение локальной последовательности
восстановления, а не допуска от сброса CPU.

Восемь префиксов ветвления останавливаются перед выбранными функциями хранения. Сброшенный
бит 4 выбирает группы внутренней flash; установленный — `0xC13550(2)`. Последующая
ветка снова проверяет этот флаг, а не внедрённые возвраты 0/3/`0xFFFF`: сброс ведёт к
группам, установка — к `0xC1055E(2,0x55D4)` после пропущенного вызова watchdog. Первая
альтернативная функция не исполняется; тесты не устанавливают, меняет ли она флаг.

Ещё 32 сценария связывают прежний производитель флага в `0xC031FC` через реальную
промежуточную функцию `0xC0AE5A` с этим ветвлением. Меняются внедрённый результат
предшествующей проверки 0/1/255/256, конфигурация 0/1, начальный бит выбора и два
посторонних набора флагов идентификации. Только ненулевой младший байт результата вместе
с конфигурацией 0 выбирает альтернативный путь. В исследованном заводском образе
конфигурация `0xC80A52` равна 1, поэтому эти сценарии от производителя до ветвления
выбирают группы внутренней flash при данном заводском байте. Конфигурация 0 — условная
подстановка в эмуляторе. Проверка, более ранняя инициализация, полный последовательный
путь и поздние изменения не исполнялись; выбор хранилища при каждом реальном запуске
этим не установлен.

Все 77 сценариев прошли. [Метаданные](data/storage-other-groups.json) содержат хеши образа,
скрипта, унаследованных скриптов восстановления/подготовки, адаптации адресов и декодера.
Эти результаты закрывают локальные пути восстановления всех восьми слотов данного образа.
Остаются полное поведение перехода с альтернативного хранилища, контекст запуска, поздние
записи флагов, смысл полей и физическое восстановление прерванной записи. Первая альтернативная
вызывающая функция проверена отдельно ниже. Общая атомарность
между группами, работающая CAN-запись и физическая сохранность не установлены.


### Альтернативная вызывающая функция и значения при пустой таблице

`tools/check_alternative_startup.py` добавляет 50 сценариев точного образа. Сорок восемь
входят в альтернативную ветку запуска в `0xC03218` и исполняют `0xC13550(2)`, заменяя
два вложенных восстановления `0xC12F10(2,0x5864)` и `0xC132CC(2)` заданными результатами.
Каждый результат меняется среди 0/1/3/`0xFFFF`. Таблица RAM в `0xE03000` содержит
82 слова: все `0xFFFF` либо нулевое слово на первой или последней позиции. Таблица
задаётся независимо от вложенных результатов. Вызовы watchdog пропускаются; вложенные
последовательные чтения и другие их эффекты в этих сценариях не исполняются.

Вызывающая функция возвращает 1 только при возврате 1 от обоих внедрённых восстановлений,
иначе 6. Независимо от этих результатов все 82 сигнальных слова вызывают
`0xC08560` -> `0xC081F0`; несигнальное слово на любом конце предотвращает вызов.
Реальный обработчик значений по умолчанию, включая короткую ветку арифметической функции,
исполняется. Проверены выбранные записи ROM/значений по умолчанию и сбросы битов вызывающим
кодом: `0xFD66` бит 14 и `0xFD5A` бит 3. Это явная политика пустой таблицы, а не
доказательство отсутствия внешней микросхемы или чтения подставленных байтов на шине.

Бит 4 выбора в `0xFD1E` остаётся установленным. Отслеживание записей не находит
сохранений в содержащее его слово в этом исполненном префиксе вызывающей функции/значений
по умолчанию; затем достигается `0xC1055E(2,0x55D4)`. В модели одни лишь ошибки
вложенных возвратов или ветка значений при пустой таблице не вызывают перехода к группам
flash. Это не исключает запись выбора внутри заменённых вложенных восстановлений,
позднего кода запуска или прерываний. Тест останавливается перед следующей альтернативной
функцией и не устанавливает полный выбор хранилища.

Ещё два сценария исполняют реальное тело `0xC132CC(2)`, его инициализатор RAM
`0xC13EB8` и функцию суммы `0xC135FE`, заменяя только последовательные чтения постоянными
сгенерированными блоками. Каждый запрашивает 544 байта с последовательного адреса
`0x0540`, за 34 чтения по 16 байт. Подставленные потоки целиком состоят из `0x00`
или `0xFF`; проверены сборка в `0x00B00C` и итоговые 42 поля дескриптора общим
размером 45 байт. Эти два исполнения возвращают 0 и сохраняют выбор хранилища. Оба
набора обходят другие зависимые от данных функции обработки полей: произвольное содержимое,
другое вложенное восстановление и полное восстановление альтернативного хранилища остаются
вне этих двух сценариев. Реальное последовательное устройство, время USIC и наличие микросхемы
не моделируются; последовательный порт не открывается.

Все 50 сценариев прошли. [Метаданные](data/alternative-startup.json) содержат хеши образа,
скрипта, унаследованного скрипта подготовки, адаптации адресов и декодера. Следующая полезная
работа — восстановление по дескриптору, проверенное ниже, и дальнейшая зависимая от данных
обработка полей, включая возможные записи выбора в этих функциях. Внедрённые вызывающему коду ошибки следует
отделять от реального отказа последовательной транзакции; ни загрузка значений по умолчанию,
ни локальный результат 6 не устанавливают переключение на другое хранилище.


### Сумма альтернативного дескриптора и связанные восстановления

`tools/check_alternative_descriptor.py` добавляет 12 сценариев точного образа. Восемь
входят в реальное восстановление дескриптора `0xC12F10(2,0x5864)`. Последовательные
чтения заменяются сгенерированными байтами; арифметические функции исполняются из прошивки
с прежними адаптациями адресов и CALLS/RETS. Функция сначала запрашивает двухбайтовую
сумму по последовательному адресу `0x0530`, затем 528 байт данных с `0x0320` за
33 чтения по 16 байт. Это аргументы на границах вызовов, а не захваты шины или
измерение ёмкости микросхемы.

Для постоянных данных `0x00`/`0xFF` каждый сценарий задаёт соответствующую 16-битную
сумму байтов, сумму с изменённым битом, сумму `0xFFFF` либо меняет последний байт
данных при прежней сумме. Совпадение возвращает 1; несовпадение возвращает 6 и
выставляет `0xFD5A` бит 3. Собранные 528 байт и 58 полей дескриптора общим размером
514 байт проверяются независимо. Поля копируются в рабочую RAM и в этих сценариях
неверной суммы: локальная ошибка не блокирует копирование. Изменение последнего байта
сохраняет распределённые поля, но меняет результат суммы, подтверждая участие хвоста
из 14 байт в проверке. Это не доказательство неинициализированной памяти ЭБУ, смысла
полей или принятия неверных данных последующим кодом.

Ещё четыре сценария исполняют вызывающую функцию запуска `0xC13550(2)` с обоими
реальными вложенными восстановлениями `0xC12F10` и `0xC132CC`, используя постоянные
сгенерированные последовательные потоки и корректную либо изменённую сумму дескриптора.
Каждый выполняет 68 моделируемых чтений: два байта метаданных, 528 байт дескриптора
и 544 байта второго восстановления. В этих сквозных сценариях вложенные результаты
не подставляются. Первое восстановление возвращает 1/6 по своей сумме; второе —
0 для обоих заданных потоков, поэтому вызывающая функция возвращает 6 во всех четырёх.
Таблица из `0xFF` вызывает реальный обработчик значений по умолчанию; нулевая — нет.

Все четыре достигают следующего альтернативного вызова `0xC1055E(2,0x55D4)` с
установленным битом 4 выбора `0xFD1E` и без отслеженных записей в содержащее его слово.
Следовательно, ошибки суммы, включая реальную локальную ветку проверки в этой модели
исполнения, сами по себе не переключают эти наборы на хранение во flash. Произвольные
зависимые от данных пути, следующее альтернативное восстановление, поздний запуск и
прерывания не исполнялись. Сохранённый выбор не является доказательством отсутствия
переключения на всех путях прошивки.

Все 12 сценариев прошли. [Метаданные](data/alternative-descriptor.json) содержат хеши точного
образа, скрипта, унаследованного скрипта подготовки, адаптации адресов и декодера. Модель
не эмулирует физическую последовательную передачу, наличие устройства, время, сброс или
полный запуск. Следующее восстановление дескриптора проверено ниже; другие зависимые
от данных пути обработки полей остаются открытыми. Неверную сумму, изменение RAM и
выбор хранилища следует считать отдельными наблюдениями.


### Восстановление копий в режиме чтения

`tools/check_redundant_descriptor.py` добавляет 11 сценариев точного образа со входами
`0xC1055E(2,0x55D4)` или `0xC1055E(2,0x569C)`. Исполняются арифметика, выбор,
сравнение и код значений по умолчанию. Последовательные чтения/записи используют явный
синтетический массив из 4096 байт; вызовы задержек считаются и пропускаются. Это не
модель последовательной микросхемы, утверждение о физической ёмкости, измерение времени
или полный запуск.

Для каждого дескриптора постоянные массивы из `0x00` и `0xFF` возвращают 0 без
вызовов записи; последний вызывает соответствующий реальный обработчик значений по умолчанию.
Ещё три сценария на дескриптор помещают единственную копию с верной суммой и нулевыми
данными на каждую возможную позицию, а в остальные — разные ненулевые данные с изменёнными
суммами. Проверены выбранные 88/315 прикладных байт. Оба пути сохраняют бит 4 выбора
`0xFD1E`, без отслеженной записи в его слово в этих сценариях, но восстановление копий
у них различается.

Для `0x55D4` вход в режиме чтения с одной корректной копией приводит к реальным
инструкциям вызова последовательной записи. Скрипт проверяет полный набор адресов/длин:
три области данных по 96 байт в `0x0000`/`0x0060`/`0x00C0`, каждая шестью блоками
по 16 байт, и двухбайтовые суммы в `0x0120`/`0x0130`/`0x0140`. Выполняется 21
вызов записи и 21 пропущенный вызов задержки; все три копии, включая исходно корректную,
становятся выбранными данными в синтетическом массиве. Функция возвращает 2. Следовательно,
режим 2 не гарантирует отсутствие записи у этой прикладной функции хранения. Не следует
вызывать её как безобидную стендовую пробу чтения или выводить защиту от записи из названия
режима.

Ещё один сценарий `0x55D4` подавляет каждый моделируемый эффект записи, продолжая
исполнять проверочные чтения прошивки. Выполняются три попытки записи тех же 21 интервалов,
всего 63 записи/задержки, возвращается 3, синтетический массив остаётся прежним. Это
проверка ограниченного программного пути отказа, а не реального ресурса памяти, времени
записи, восстановления при её прерывании или физического обнаружения ошибки.

Для `0x569C` три сценария с одной корректной копией восстанавливают 315 прикладных
байт и возвращают 0 без последовательных записей/задержек. Синтетический массив остаётся
прежним. Области копий начинаются в `0x0150`/`0x0290`/`0x03D0`, по 320 байт на
область, суммы находятся в `0x0510`/`0x0520`/`0x0530`. Эти сценарии не доказывают
отсутствие записи на каждой ветке большой функции или одинаковое поведение произвольных
неверных данных.

Все 11 сценариев прошли. [Метаданные](data/redundant-descriptor.json) содержат результаты
синтетических сценариев и хеши образа, скрипта, унаследованного скрипта подготовки, адаптации
адресов и декодера. Физическая последовательная передача, сброс, операции flash и полный
запуск не выполняются. Остаются обработка непостоянных данных и поздние записи запуска/выбора.
Путь автоматического восстановления — ещё одна причина отделять прикладную инициализацию
от проверенной операции чтения загрузчика без записи.


### Вложенные вызовы подготовки и эффекты последовательного обмена

`tools/survey_reset_callees.py` расширяет статический обход от `0xC0D572` по вложенным
прямым вызовам, ветвям и продолжениям. На точном исследованном образе I444GI04 он посещает
5469 адресов и фиксирует 42 цели прямых вызовов, 67 мест возврата и единственный
`SRST` в `0xC0D6B8`. Это синтаксические счётчики графа, а не независимо исполненные
функции или доказательство достижимости всех условных путей.

Четыре аннотации точных байтов закрывают DSP-пробел установленного декодера:
`0xC5EA76`, `0xC5EA7A`, `0xC5EA7E` и `0xC5EA84` — CoMULu, CoSHL, CoMACu и CoSUBR.
Их четырёхбайтовые кодировки и последовательный поток сверены с руководством Infineon
[C166S V2](https://media.digikey.com/pdf/Data%20Sheets/Infineon%20PDFs/C166S_V2_UM_V1.7_Jan2001.pdf),
разделы 7 и 8. Граф добавляет только рёбра к следующей инструкции; аккумулятор,
флаги, изменения указателя стека и чтение данных не эмулируются. Байты прошивки и
установленный декодер не меняются. В отчёте больше нет неразрешённой границы прямого потока.

Буквальный поиск исследованных регистров сброса и адресов входа загрузчика показывает
только существующий `SRST`; новой записи конфигурации сброса или прямого входа в загрузчик
он не обнаруживает. Это не доказательство отсутствия: косвенные/вычисляемые записи,
прерывания, другие источники сброса и эффекты исполнения остаются вне результата. Граф
без неразрешённых переходов не доказывает назначения вычисляемых записей.
[Отчёт графа](data/reset-callees.json) показывает аннотации и рёбра прямых вызовов.

Цепочка вызовов подготовки также достигает функций последовательного обмена `0xC10060`
и `0xC101F8`. Этот синтаксический граф не специализирует все условия функций под
фактические аргументы подготовки; исполнение каждой транзакции для `0x90` не доказано.
Статический разбор устанавливает конкретную границу побочных эффектов:

- Обе обращаются к странице `0x81` и смещениям блока `0x0800`, включая записи по
  `0x0880`, опрос `0x0844` и чтения по `0x085C`.
- База канала `0x204800` соответствует U1C0 в руководстве периферии XC2000,
  таблица 19-29; смещения передающего буфера, статуса протокола и приёмного буфера
  соответствуют разделу 19.2.1.2 ([manual](https://www.keil.com/dd/docs/datashts/infineon/xc2000_per_um.pdf)).
  Это определяет путь последовательной периферии; физическое устройство и разводка не проверены.
- Первая функция записывает константы `0x06`, затем `0x02`, после старший и младший
  байты аргумента адреса и данные из RAM. Вторая записывает `0x03`, передаёт аргумент
  адреса и собирает принятые данные в RAM. Эти последовательности инструкций согласуются
  с гипотезой записи/чтения последовательной памяти, а не определяют микросхему.
- На этих путях есть циклы по статусу и обслуживание watchdog. Ни прошедшее время,
  ни успешное завершение на реальной периферии статическим обходом не установлены.

Поэтому путь подготовки `0x90` не установлен как перезапуск, затрагивающий только RAM
или не имеющий побочных эффектов. Кроме подготовки состояния он достигает операций
последовательной передачи/приёма; для использования его в эксперименте входа нужно
установить назначение и эффекты. Здесь не выполнялись транзакции периферии, операции
энергонезависимой памяти или сброс. Более простая ветка `0x01` сама по себе также
не устанавливает программный вход в загрузчик.

```
python tools/survey_reset_callees.py IMAGE.bin --report reset-callees.json
```

Инструмент отвергает другие хеши образов и использует новый импорт Ghidra без записи.
Ошибки декодирования и неразрешённые переходы сообщаются как границы; исчерпание бюджета
и ошибки скрипта завершают обследование ошибкой. Маркер успеха означает завершение
ограниченного обследования, а не проверку всего пути сброса. Экспортируются адреса
и метаданные, а не байты прошивки. Следующие офлайн-цели — назначения вычисляемых
записей и протокол последовательного устройства; выводить их из названия службы сброса нельзя.

`tools/check_serial_preparation.py` исполняет обе последовательные функции и их проверенные
функции настройки на сгенерированных данных. Все 34 сценария прошли: 32 сценария с
удерживаемой готовностью проверяют чтение/запись, четыре адреса и длины 0, 1, 2 и 16;
2 участка с удерживаемой неготовностью остаются в опросе статуса. Записи GPIO в бит 2
`0xFFB6` обрамляют обмены: функция записи отделяет `0x06` от `0x02` с адресом/данными
переходом высокого уровня в низкий; функция чтения обрамляет `0x03` с адресом/пустыми
передачами. Системное руководство определяет этот регистр как P10_OUT; предполагаемый
сигнал выбора — P10.2, а не доказанное соединение платы. Обе функции передают минимум
один байт данных даже при нулевой длине, поскольку проверка длины идёт после передачи.
Приёмный буфер и источник записи находятся в `0xE023EB`.

[Отчёт последовательного обмена](data/serial-preparation.json) содержит хеши образа и скриптов.
Модель удерживает статус протокола готовым, подставляет байты приёма и заменяет командные
порты RAM. Вызовы watchdog явно пропускаются; время, сдвиговый регистр, физическая
микросхема, защита и энергонезависимые операции не моделируются. Тесты входят прямо
в функции; они не доказывают выполнение конкретной транзакции реальной подготовкой
сброса `0x90`. Для определения назначения всё ещё нужны свидетельства платы или
независимо установленный протокол устройства; одних констант команд недостаточно.

Проверка последовательного обмена также сверяет инструкции вызывающей функции и таблицу
констант при исследованном отображении DPP приложения. Таблица задаёт предел данных
320 байт, адреса данных `0x0150`, `0x0290`, `0x03D0` и адреса метаданных `0x0510`,
`0x0520`, `0x0530`. Вызывающая функция загружает эти адреса, вызывает запись, затем
чтение, сравнивает принятые байты с сохранённой копией RAM и при несовпадении фиксирует
локальное значение ошибки 3. Это статические свидетельства гипотезы хранения нескольких
копий состояния в последовательной памяти. Они не измеряют ёмкость, не определяют
смысл полей и не доказывают запись всех копий при реальном сбросе. Численные функции,
полное исполнение вызывающей функции и завершение внешней памяти остаются вне проверки
последовательных функций. Эти локальные адреса последовательного устройства нужно
отделять от адресного пространства flash MCU.

### Диагностические разборщики пути сброса

Теперь декодированы конкретные локальные связи диспетчера: байт выбора `0x11` достигает
вызова по `0xC505BE`, через `0xC5D48A` в разборщик `0xC57F8E`; второй путь вызывает
по `0xC603EA`, через `0xC6AD5E` разборщик `0xC666DC`. Эти локальные связи вызовов не
устанавливают внешнюю достижимость, физический транспорт или все проверки сессии/доступа.

Прежний найденный писатель `0xC5028A` нельзя считать источником именно пути сброса:
его декодированный вызов по `0xC55D54` относится к разборщику, проверяющему байт выбора
`0x83` по `0xC55CD6`. Несколько служб используют общую ячейку аргумента. Совпадение
адреса назначения само по себе не доказывает поток данных от входящего запроса сброса.

| Разборщик | Вход и проверки на исследованном пути | Локально принимаемые значения аргумента |
|---|---|---|
| `0xC57F8E` | Буфер по `0xE01212`; аддитивная контрольная сумма, объявленная длина полезных данных 2, байты заголовка `0x10` и `0xF1`, байт выбора `0x11`; копирует следующий индексируемый байт в логический `0xDE64` по `0xC58060` | `0x01`, `0x90` |
| `0xC666DC` | Байт выбора по `0xFA54` равен `0x11`; копирует `0xFA55` в логический `0xDEE9` по `0xC666F2` | `0x01`, `0x90`, `0x91` |

Второй физический источник следует из явного `EXTP 0x3`; ячейки аргумента/статуса —
логические адреса при состоянии DPP приложения. Этот локальный разборщик не проверяет
длину или контрольную сумму; это не устанавливает, делает ли проверку его вызывающий код.
Оба разборщика сохраняют аргумент до его проверки. Значение, оставшееся в RAM после
отклонения, не означает приёма операции: нужно проверять ячейку статуса.

В ограниченной модели `0x01` выбирает короткий путь функции сброса, а `0x90` — подготовку.
Известные вызывающие ветви сброса второго пути явно пропускают `0x91`, хотя разборщик
его принимает. Путь последующей обработки по `0xC6671A` обрабатывает его отдельно.
Поэтому успех разборщика нельзя приравнивать к исполнению `SRST`. Функции последующей
обработки по `0xC5808C` и `0xC6671A` также обрабатывают `0x90` через дополнительные
вызовы; их полные эффекты и порядок предшествующей обработки вне проверки разборщика.

Воспроизводимая проверка Ghidra теперь исполняет оба разборщика на сгенерированных
входах RAM, с тождественными страницами DPP и явными обвязками EXTP/адресных userop.
Для первого разборщика все 256 значений аргумента проверены в каждой из 2 форм кодирования
длины: 512 случаев, из них 4 приняты. Второй разборщик охватывает 256 значений, из них
3 приняты. Ещё 11 отрицательных случаев проверяют испорченную контрольную сумму,
изменённые заголовок/байт выбора и неверную длину. Для примеров неверной длины контрольная
сумма пересчитана, чтобы независимо проверить её отклонение. Наблюдаемые локальные
статусы первого разборщика: `0x77` при неверной контрольной сумме, `0x12` при неверной
длине и `0x11` при исследованных ошибках заголовка/байта выбора. Это значения статуса
в RAM, а не проверенные байты ответа CAN.

В этой части исполняются только инструкции разборщика: диспетчер, сброс, последующая
обработка, конвейер приёма периферии и процедура авторизации не исполняются. Выбранные
проверки допуска префикса диспетчера охвачены отдельно ниже. Тест не доказывает,
что какой-либо синтетический вход можно доставить этим функциям на физическом ЭБУ.
Он добавляет локальные свидетельства проверки входных данных, но программный вход в
CAN-загрузчик остаётся неустановленным. Следующая полезная работа — проследить приём
буферов и проверить все условия диспетчера, а не угадывать команду программирования по
знакомому диагностическому байту выбора.

### Локальные условия допуска перед диагностическими разборщиками

Вход диспетчера второго пути по `0xC602B4` читает байт состояния по физическому
`0x00C704` через `EXTP 0x3`. Его локальный поток строже прямого вызова разборщика
с заполненным буфером:

| Место | Условие | Следующее действие на исследованном пути |
|---|---|---|
| Вход | Состояние равно `0xFF` | Переход на `0xC607A4`, минуя исследованный префикс диспетчеризации разборщиков |
| Вход | Состояние отличается от `0xFF` | Вызов `0xC48478` |
| После этого вызова | Возвращённое `r4` | Сохранение значения по `0xE01656` |
| Повторное чтение состояния | Состояние равно `0x00` | Вызов `0xC679C4`, затем сохранение возвращённого байта выбора для диспетчера |
| Повторное чтение состояния | Состояние отличается от `0x00` | Переход к альтернативной обработке по `0xC60792` |

Один источник байта состояния из завершения транспорта определён ниже; изменения во
время этих вызовов и все остальные источники здесь не проверены.
Нельзя называть его значения каналами CAN, уровнями авторизации или измеренными состояниями
приёма. Короткая функция по `0xC48478` лишь читает логический `0xC674` в `r4`; она не
измеряет кадр независимо. Функция получения байта выбора по `0xC679C4` читает `0xFA54`
при явном выборе страницы. Ни одна из них не доказывает поступления сообщения, владения
им или согласованности длины. Альтернативная ветвь этой проверкой не исполняется.

Тест Ghidra добавляет 511 синтетических случаев допуска: все 256 начальных значений
байта состояния до первого вызова/пропуска и 255 состояний после получения значения,
исключая значение начального пропуска. Для последних тест подставляет результат 2 в
`r4`, проверяет его запись в RAM и останавливается перед получением байта выбора либо
альтернативной обработкой. Он не вызывает функцию получения значения, не моделирует
поступление, не устанавливает продвижения и не исполняет весь диспетчер. Изменения
состояния во время получения значения не охвачены. Применяются те же явные обвязки
DPP/EXTP и проверки ошибок.

Первый путь также начинается со сравнения битов по `0xC50442` и условного перехода
по `0xC50446` до вызова функций заголовка. Смысл/источники этих битов и все последующие
условия допуска не установлены. Его общий буфер `0xE01212` также заполняют пути
построения сообщений приложения, например по `0xC5946C`. Поэтому одна запись в этот
буфер не определяет путь приёма периферии.

Эти локальные проверки допуска не устанавливают приём на физической шине, полную
последовательность сессии/доступа или программный вход в CAN-загрузчик. Отдельная
трассировка приёма/копирования ниже определяет ID приёма приложения; нельзя назначать
этим диагностическим функциям идентификаторы загрузчика.

### Путь приёма CAN приложения во второй разборщик сброса

Для точного исследованного образа I444GI04 второй диагностический путь теперь можно
проследить до драйвера MultiCAN в программе. Это отдельный механизм от стартового обмена
загрузчика во flash, и он не устанавливает программный вход в этот загрузчик.

Драйвер по `0xC47218` читает регистры арбитража/данных/DLC объекта сообщений при странице
`0x80`. На исследованном пути извлечения стандартного идентификатора он маскирует
старшее слово арбитража и сдвигает на 2, затем вызывает `0xC477C8` по `0xC47302` с ID,
длиной и скопированными данными. Интерпретация регистров опирается на то же руководство
MultiCAN, указанное ниже. Программный диспетчер ищет в 16 записях по 10 байт.
Старт приложения задаёт `DPP1=0x320`, поэтому логическая таблица по `0x6C2C`
отображается на `0xC82C2C`.

Две записи выбирают вызов транспорта по `0xC47836`, а не другого обработчика сообщений:

| CAN ID приёма | Дескриптор приёма приложения | PDU транспорта | Итоговый буфер полезных данных |
|---|---|---|---|
| `0x7DF` | `0x15` | `0x29` | `0xFA54` |
| `0x7E0` | `0x16` | `0x2A` | `0xFA54` |

Транспорт по `0xC481D2` обрабатывает кадрирование и вызывает функцию копирования/обработки
по `0xC4861E`. Она получает назначение через `0xC49A12` и копирует туда полезные байты.
Дескрипторы маршрутизации/буферов приходят из записи инициализации приложения по
`0xC049A2`: декодированный интерпретатор таблицы копирования загружает 26 байт из
`0xC499F8` в `0xC702`. Это задаёт привязки PDU приёма и указатель назначения.
Путь завершения вызывает `0xC49B1E`; его ветка совпавшего PDU сохраняет переданный
байт результата в логический `0xC704` по `0xC49B30`. Успешный путь копирования передаёт
ноль. Это связывает результат завершения транспорта с описанным выше условием диспетчера.
Динамическое копирование, маршрутизация и доступы RAM предполагают моделируемое
состояние `DPP3=0x3`; поведение сброса/ROM и все промежуточные изменения страниц не эмулируются.

Проверка Ghidra добавляет 6 связных программных случаев: оба ID приёма с каждым из
3 локально принимаемых аргументов второго разборщика. Сгенерированный короткий кадр
поступает на вход `0xC477C8`; реальные инструкции прошивки выполняют поиск по таблице,
проверки кадрирования, выделение назначения, копирование данных и уведомление завершения.
Модель проверяет полезные данные в `0xFA54`, длину 2 и нулевой результат завершения,
затем запускает разборщик `0xC666DC` и проверяет принятые аргумент/статус. Ещё 4 случая
проверяют оба ID с неподдерживаемым полубайтом типа кадра или объявленной длиной
короткого кадра, слишком большой для переданного кадра. Они оставляют начальное
сигнальное значение завершения и диагностический буфер неизменными.

CALLS/RETS используют явный стек возвратов хоста. Пример моделирует RAM, DPP/адресные
userop, флаг разрешения транспорта и состояние контроллера; фактическая инициализация
контроллера не исполняется. Разрешены лишь исследованные вызываемые функции; неизвестные
userop, вызовы, исчерпание бюджета или чтение неинициализированной памяти завершают
проверку ошибкой. Реальный цикл приёма MultiCAN исследован статически, а не исполнен
на модели периферии. Кадр на шине, ACK CAN, интервалы, физическая разводка, полный
диспетчер диагностики, процедура доступа, последующая обработка и сброс не проверяются.
Эти условия включены в [отчёт](data/application-reset.json).

Это устанавливает программный путь от приёма CAN приложения до второго разборщика
сброса при явных допущениях модели. Это не устанавливает допуск запроса сброса через
всю цепочку на оборудовании. Путь буфера передачи отдельно проверен ниже; полные условия сессии/доступа
не установлены. Загрузчик во flash по-прежнему использует отдельно выведенный обмен
`0x100`/`0x101`; нельзя подставлять вместо него ID приложения. Первый путь аргумента
через `0xE01212` всё ещё требует собственной трассировки физического приёма. Совпадение
загрузочных префиксов не оправдывает перенос таблиц приложения на другие версии прошивок.

### Диагностический буфер передачи приложения

Для того же точного образа `0xC49AFC` передаёт буфер `0xFB53` с длиной из
`0xE01704` и PDU `0x2B` в `0xC47C7E`. Функция использует запись `0xC82D00`
для подготовки контекста транспорта. Периодическая функция `0xC47E2A` собирает кадр
и передаёт его через `0xC48178` в `0xC47586`. Выбранный дескриптор драйвера — `0x0C`;
его запись `0xC82C18` задаёт ID `0x7E8` и объект сообщений 92. Драйвер
`0xC46F84` копирует ID/DLC/данные и выдаёт команду запроса передачи. Таким образом,
обратный путь связан программно, а не выведен из константы ID.

`tools/check_application_can_tx.py` исполняет этот путь, включая обратный вызов буфера,
получение состояния контроллера, функции критической секции и уведомление о завершении.
Все 9 сценариев прошли: сгенерированные данные длиной 1, 2 и 7, для каждой длины
сразу доступный объект либо удерживаемый бит статуса 2 или 8 с последующим освобождением.
Кадры имеют DLC 8, байт длины одиночного кадра и заполнение `0xAA`. При занятости
собранный кадр сохраняется; изменение исходного буфера перед следующим периодическим
вызовом не меняет скопированные данные кадра в этих сценариях.
[Метаданные](data/application-can-tx.json) фиксируют хеши точного образа, скрипта,
общей адаптации и найденного декодера.

Модель задаёт состояния контроллера, разрешение драйвера, валидность/список объекта
сообщений и дескрипторы RAM, включая регистр арбитража стандартного кадра. Драйвер
сохраняет биты формата кадра; модель не проверяет их аппаратную инициализацию. Записи
команд регистров — обычные записи RAM без аппаратных эффектов. Арбитраж CAN, ACK, прерывание завершения передачи и тайминг не
моделируются. Постановка на передачу и обычное программное уведомление не доказывают
доставку по шине. Тест начинается с API буфера передачи со сгенерированными данными,
а не с диагностического запроса: допуск, построение ответа службой, сессия/доступ и
программный вход в загрузчик остаются непроверенными. Нельзя считать сгенерированные
байты захваченным ответом сброса или переносить адреса приложения на другие образы.

## Настройка CAN

Функция `0xC00370` обращается к регистрам MultiCAN. Раздельная раскладка регистров
из руководства по периферии XC2000 даёт следующую интерпретацию:

| Адрес регистра | Записанное значение | Интерпретация |
|---|---|---|
| `0x200300` | `0x0041`, далее сброс битов настройки/инициализации | Настройка узла 1 |
| `0x20030C` | `0x0001` | Вход B приёмника узла; подключение на плате ещё требует проверки |
| `0x200310` | `0x3443` | Битовые интервалы узла |
| `0x20101A` / `0x201018` | `0x8400` / `0x0000` | Стандартный идентификатор `0x100` объекта 0 |
| `0x20103A` / `0x201038` | `0x4404` / `0x0000` | Стандартный идентификатор `0x101` объекта 1 |

Стартовый приёмник опрашивает объект 0; стартовый ответ передаёт индекс объекта 1
в `0xC004F2`. Следовательно, код указывает на ID приёма `0x100` и передачи `0x101`.
Эти идентификаторы выведены из записей регистров, а не измерены на шине.

Для `0x3443` поля битовых интервалов: `BRP=3`, `SJW=1`, `TSEG1=4`, `TSEG2=3`,
`DIV8=0`. С учётом кодируемых приращений получаются 10 квантов на бит,
предделитель 4 и точка выборки 60%. Поэтому `bitrate = fCAN / 40`.
Запись делителя CAN по адресу `0xC00380` устанавливает `0x43FE` в `0x20000C`.
Это обычный режим делителя с `STEP=1022`: `fCAN = fSYS / 2`, следовательно,
`bitrate = fSYS / 80`.
Инициализация частоты завершается значениями `PLLCON0=0xA704` после отключения обхода,
`PLLCON1=0x8100` (кроме самосбрасывающегося запроса проверки захвата) и
`PLLCON3=0x8003`. Поля делителей: `N=40`, `P=2`, `K2=4`; выбран вход внешнего
генератора. Если системная частота поступает по этому пути PLL,
`fSYS = 5 * fOSC` и `bitrate = fOSC / 16`. Указанный в документации стендовый кварц
8 МГц тогда означал бы 500 кбит/с. Состояние мультиплексора системной частоты при
входе во flash пока не установлено; это условный результат, а не измеренная скорость.
Ограниченные циклы задержки пока не устанавливают длительность стартового окна
в миллисекундах.

### Выводы микроконтроллера

Выбор порта узла 1 значением `0x0001` включает вход B приёмника. Даташит XC2765X
связывает его с `P0.4`, выводом корпуса 63. По адресу `0xC003AE` загрузчик пишет
`0x0090` в `0xE844` — регистр управления выводом `P2.2`. Выбирается двухтактный
альтернативный выход 1, который даташит связывает с передачей узла 1, выводом корпуса 41.
Это соответствия внутри микроконтроллера, а не прозвонка до трансивера или разъёма
платы. Они отличаются от пары выводов ROM CAN BSL, описанной в FINDINGS.md.
Для такого пути нужен установленный CAN-трансивер; L9637D обслуживает другой
физический интерфейс — K-line — и в этих путях регистров CAN не используется.

## Стартовый обмен и согласование сессии

Ниже приведены статические условия приёма; смещения байтов отсчитываются от
регистров данных объекта 0. `token` — принятый байт со смещением 1, копируемый
в ответ со смещением 2. Это наблюдения декодера, а не инструкция отправки кадров в ЭБУ.

| Стадия | Условие приёма | Байты ответа, формируемые кодом |
|---|---|---|
| Старт, `0xC002E4` | байт 0 = `0x01`, байт 2 = `0x96`, байт 3 = `0x69` | `FF 00 token 69 96 69 ?? ??` |
| Сессия, `0xC005BC` | байт 0 = `0x01`, слово little-endian со смещением 2 = `0x0002` | `FF 00 token FE 01 00 00 00` |

Первый обмен устанавливает флаг CPU и запускает цикл команд. Флаг сессии в RAM
он не устанавливает. Инициализация в `0xC00964` обнуляет это состояние. Второй обмен
устанавливает бит 5 в `0xA404`; остальные коды команд игнорируются, пока бит не установлен.
Второй ответ включает запись по адресу `0xC00616`, пропущенную в исходном
проанализированном листинге и восстановленную декодированием очищенного рабочего окна.
Это согласование состояния сессии; отсутствие других проверок авторизации
для отдельных команд из этого не следует.

Передающая функция `0xC004F2` копирует 8 байт в объект 1. В стартовом ответе
исследованный успешный путь задаёт только первые 6 байт; последние 2 байта
нельзя считать нулевыми или использовать как фиксированную сигнатуру ответа.
Стартовый обработчик проверяет флаг `NEWDAT` и указанные байты, но
явно не проверяет принятый DLC на этом пути. Это не доказательство допустимости
коротких CAN-кадров.

Успешный стартовый путь явно не сбрасывает флаг `NEWDAT` объекта 0
перед входом в цикл команд. Поэтому после очистки буфера ответа цикл может
снова встретить тот же кадр. Нужен захват, чтобы установить, появляется ли
дополнительный ответ; хосту нельзя считать сессию готовой лишь на основании
ожидаемого единственного подтверждения. Последовательность на шине не проверена.

## Операции и ограничения

Диспетчер по адресу `0xC00642` сравнивает команды `0x07`, `0x02`, `0x10`, `0x18`
и `0x0E`. Исследованные пути достигают стирания сектора в `0xC00A58`, записи
страницы в `0xC00A82` и вычисления CRC с полиномом `0xEDB88320`. Путь записи
буферизует 128 байт. Команда массовой выгрузки flash в этом диспетчере не найдена.
Это не доказывает отсутствие чтения памяти во всех диагностических путях приложения.

Перед стендовым экспериментом: установить точную частоту и подключение выводов,
проследить формат стартового кадра и флаги приёма, проверить все пути команд
и авторизации. Сверить декодирование с независимым захватом или контролируемой
эмуляцией. Доступ к оборудованию и любые операции стирания/записи требуют
отдельного явного разрешения.


### Декодированные пути команд

Адреса ниже относятся к I444GI04. Для всех операций ниже нужен флаг сессии в RAM.
Многобайтовые значения имеют порядок little-endian; токен кадра отделён от
полей адреса и длины.

| Команда | Обработчик | Статическое поведение |
|---|---|---|
| `0x07` | `0xC00668` | Сброс флага сессии; не сброс CPU |
| `0x02` | `0xC00674` | Установка адресного слота, выбранного байтом 2, с селектором меньше 2; значение из байтов 4–7 |
| `0x10` | `0xC006A6` | Стирание от слота 0 на длину из байтов 2–5 с шагом `0x1000` |
| `0x18` | `0xC0077A` | Добавление количества байтов из байта 2, данные с байта 3; запись полного буфера |
| `0x0E` | `0xC00876` | CRC от слота 0 на длину из байтов 2–5; результат в байтах ответа 4–7 |

Для стирания нужен непустой интервал внутри `[0xC02000, 0xC90000)` с началом и концом,
выровненными на `0x1000`. Конец исключён и может равняться `0xC90000`.
Запись проверяет начальный адрес по тем же границам и выравниванию на
`0x80`. Количество байтов фрагмента больше 5 или сумма в буфере больше 128 отвергаются.
Функция записи страницы вызывается только после накопления 128 байт. Сообщаемый
текущий адрес растёт на 4 при каждом принятом фрагменте независимо от числа его байтов.
Эта асимметрия требует захвата: нельзя предполагать, что произвольные размеры
фрагментов дают корректную реализацию хоста. Адресный слот 1 принимается установщиком,
но его потребитель в этих обработчиках стирания/записи/CRC не найден.

CRC проверяет непустой интервал по тем же границам, без проверки выравнивания
в исследованном обработчике. Неверные параметры ведут к статусу `0x32`; начальная
проверка условий записи использует `0x33`; неизвестная команда — `0x30`. Это наблюдаемые
байты статуса, а не полная спецификация ошибок или авторизации.

### Завершение flash-операций и обработка ошибок

Для точного stock-образа I444GI04 функция `0xC009CA` опрашивает `0xFFFF06`, пока
биты 0–2 не станут нулевыми. Затем она сохраняет снимки `0xFFFF08` и `0xFFFF0A`.
Биты 0 или 1 первого снимка вызывают запись команды `0xF5`; биты 4 или 5 этого
снимка либо бит 4 второго вызывают запись `0xF0` и возврат 1. Иначе возвращается 0.
После этих записей снимки в том же вызове не перечитываются.
[Системное руководство XC2000](https://www.keil.com/dd/docs/datashts/infineon/xc2000_sys_um.pdf),
раздел 3.9, определяет эти регистры как IMB_FSR_BUSY, IMB_FSR_OP и
IMB_FSR_PROT, биты ошибок как SQER/OPER/PROER, команды как Clear Status
и Reset to Read. Применимость руководства семейства к точной модификации требует
проверки silicon/errata.

Цикл стирания в `0xC00754` и функция страницы в `0xC00AE2` при возврате 1
повторяют только вызов проверки состояния. Команду стирания или последовательность
программирования страницы они не повторяют. В функции страницы `0xC00AA4` также
ожидает сброса busy-бита 2 перед загрузкой 64 слов. В этих циклах нет счётчика
попыток или выхода по тайм-ауту; бюджет инструкций теста не является измеренным
сроком ожидания устройства. Сбросы и прерывания вне этих функций не моделируются.

`tools/check_flash_completion.py IMAGE --report REPORT` исполняет реальные инструкции
проверки состояния и записи страницы с синтетическими регистрами и существующими
адаптациями адресации/вызовов C166. Все 38 сценариев прошли: 32 сочетания битов
операций/ошибок, 3 ограниченных участка с удерживаемой занятостью и 3 сценария
страницы: сразу готово, ошибка с последующим снятием флага, постоянная ошибка.
При исчезающей ошибке функция возвращается после двух проверок состояния, но только
одной последовательности загрузки страницы и одной последовательности команды записи.
При постоянной ошибке опрос продолжается в пределах проверенного участка. Значит,
снятие ошибки может привести к обычному возврату без повторения записи и обратного
чтения; это результат модели потока управления, не доказательство успешной или
неудачной записи на микросхеме.
Метаданные и хеши исходников: [flash-completion.json](data/flash-completion.json).
Отдельная модель диспетчера с 41 сценарием по-прежнему обходит flash-функции;
её область проверки не изменилась. Новый тест заменяет командные порты flash обычной
памятью эмулятора, не моделирует физику flash и не выдаёт подтверждение CAN.

Будущий писатель должен независимо проверять содержимое после подтверждённой операции.
Отсутствие подтверждения оставляет результат неопределённым; слепой повтор фрагмента
страницы может добавить его дважды, а перезапуск сессии не очищает неполную страницу.
Эти тесты не устанавливают процедуру восстановления после потери питания или повреждения
приложения. До реализации записи нужны полная резервная копия и стендовая проверка
входа и восстановления.

Допустимый интервал загрузчика содержит 581632 байт. Полный эталонный образ содержит
851968 байт: загрузочный сектор и область с `0xC90000` находятся вне исследованного
интерфейса CRC/записи. Исключённый хвост I444GI04 не является равномерно пустым.
CAN-писатель не может считать полный образ данными без ограничений по адресам.

### Гипотеза: чтение ограниченной области через короткие запросы CRC

Отсутствие команды выгрузки само по себе не делает допустимую область нечитаемой.
Декодированный CRC — отражённый CRC32 с начальным значением из единиц, полиномом
`0xEDB88320` и финальным дополнением. Обработчик, по-видимому, допускает длину 4.
Для сообщения фиксированной длины в четыре байта CRC32 — аффинное отображение
32 бит в 32 бита; его двоичная матрица имеет ранг 32, поэтому четыре байта
однозначно восстанавливаются из CRC. Полный перебор всех четырёхбайтовых сообщений
не требуется.

`tools/check_can_crc_hypothesis.py` воспроизводит таблицу/байтовый шаг по листингу,
сравнивает результат с CRC стандартной библиотеки и обращает это независимое
отображение методом исключения в двоичной матрице. На macOS прошли проверка известного
ответа, 290 четырёхбайтовых случаев и все 256 однобайтовых CRC. Для каждого из образов
I444GI04, I414DB02 и I465AI01 все 145408 четырёхбайтовых диапазонов допустимой области
точно восстановились из локально вычисленных CRC. Восстановленные байты инструмент
не экспортирует.

Это доказывает математическое восстановление для моделируемого алгоритма, а не
работу чтения ЭБУ. Остались предположения: реальная служба принимает короткие
повторные запросы, возвращает моделируемый CRC запрошенных байтов flash и не имеет
дополнительных ограничений при исполнении. Эти математические проверки не исполняют
инструкций CPU; отдельная ограниченная проверка p-code ниже исполняет обработчики
с моделями периферии. CAN-трафик остаётся непроверенным. Метод охватывал бы только допустимый интервал; он не даёт полного бэкапа
и не читает защищённый загрузочный сектор. Скорость не измерялась.

Гипотеза не даёт оснований ослаблять требование полного бэкапа текущего писателя.
Поддержка записи CAN требует отдельного решения по покрытию образа, восстановлению,
подтверждению завершения записи и совместимости; офлайн-инструменты транспорт CAN
не включают.

## Сравнение доступных образов

Офлайн-проверка на macOS сверила SHA256 и размер с внешней описью для
120 файлов M74/M74 CAN. Это число файлов, а не независимых ЭБУ или аппаратных тестов.
Первые `0x2000` байт образуют 3 точные группы:

| Вариант | Файлов | Представитель | SHA256 загрузочной области |
|---|---|---|---|
| early | 5 | I414DB02 | `a7162971cbbdaeebf8d9ae421220b981df64bcbd4bc876b503a7304ec2a0df99` |
| common | 107 | I444GI04 | `7f1fd47c391a68460ebf3cfb78c0679c24e75470fd9787e368eb48032804310e` |
| common-tail | 8 | I465AI01 | `eb269ea46fe7432742f1d321ebe711cbf8a34b7aa1a03f78e6afaca4e2c84c7b` |

Файлы common и common-tail имеют одинаковые первые `0xDAA` байт; различия
между группами находятся только по смещениям с `0xDAE` до `0x1FFF`. Это равенство
байтов, а не доказательство ненужности хвостов. В группу early входят I414DA01,
I414DB02, I414DC03, I444CB02 и I444CC03. I414DA01 по описи — досерийный образ;
нельзя превращать его в аппаратный эталон.

Отдельный дизассемблерный разбор I414DB02 подтверждает развилку по причине сброса,
стартовые условия, CAN ID, интервалы узла, ветви команд и допустимый интервал.
Адреса отличаются: развилка сброса `0xC002A6`, диспетчер `0xC00646`, CRC `0xC0087A`.
Ранняя инициализация также вызывает периферийную функцию по адресу `0xC00DA0`,
отсутствующую в общем пути. Равенство исполнения не проверялось; нельзя применять
единую карту адресов ко всем образам. Сравнение common-tail опирается на равенство
байтов исследованного префикса, а не ещё одну независимую аппаратную проверку
или исполнение CPU.

Таблицы свидетельств содержат только имена файлов, длины и хеши:
[data/can-loader-images.csv](data/can-loader-images.csv) и
[data/can-loader-controls.csv](data/can-loader-controls.csv).
Вторая охватывает 47 контрольных файлов: 2 M74K и 45 M73, уже вне текущей поддержки.
Ни один не совпадает с исследованными хешами загрузочных областей. Неизвестный хеш
не доказывает отсутствия загрузчика и не должен определять архитектуру CPU.

Повторить проверку байтов: `tools/survey_can_loader.py DIR --csv report.csv`.
Инструмент классифицирует только исследованную загрузочную область, а не совместимость
полного образа. Переименование файла, знакомый размер или совпадение лишь префикса
не устанавливают совпадения с исследованной областью.
Границы поддержки остальных блоков: [ECU_SUPPORT.md](ECU_SUPPORT.md).


## Ограниченное исполнение обработчиков прошивки

`tools/check_can_loader_emulation.py` импортирует каждый заданный сырой образ в новый
рабочий проект Ghidra только для чтения по адресу `0xC00000`. Он запускает
`tools/ghidra/EmulateCanLoader.java` через p-code модуля C166. Генератор таблицы CRC,
байтовый цикл CRC, проверки адресов, флаги сессии, сборка фрагментов и копирование
буфера передачи исполняются из инструкций образа; формула CRC из Python их не подменяет.

На Darwin arm64, Ghidra 12.1.4, язык `C166:LE:16:default`, прошли все 41 сценариев
для каждого из I444GI04, I414DB02 и I465AI01. Хеши всей загруженной памяти сверены
с входными файлами. [Отчёт метаданных](data/can-loader-emulation.json) фиксирует эти
хеши, хеш скрипта и отпечаток декодера, найденного в установке. Последний определяет
найденный скомпилированный модуль, а не независимо проверяет всё окружение Ghidra.
Модуль должен поддерживать JMPA с предсказанием и адресные служебные операции,
реализованные скриптом; произвольный пакет C166 ему не эквивалентен.

Границы модели исполнения заданы явно:

- CALLS/RETS используют стек возвратов хоста; адресация EXTP/EXTS/DPP — обработчики.
- RAM начинается с явного заполнения; хост входит в точки обработчиков/цикла, а не
  исполняет сброс кремния, старт ROM или инициализацию частот периферии.
- Данные/DLC CAN и флаг `NEWDAT` подставляются в регистры объектов сообщений.
  Сброс флага немедленный; фильтрация приёма, арбитраж, ACK шины и интервалы не моделируются.
- Функции стирания/записи flash фиксируют синтетические операции; обработчик состояния
  подменён немедленным ответом готовности. Физическая запись, восстановление после ошибки
  и обратное чтение не проверяются. Адаптер не открывается, восстановленная прошивка не экспортируется.
- Неизвестные служебные операции, исчерпание лимита инструкций, ошибки скрипта или
  отсутствие финального маркера приводят к провалу проверки. Код выхода Ghidra сам по себе
  не доказывает успеха.

Это ограниченная проверка исполнения инструкций на стороннем декодере, а не полная
или потактовая валидация C166SV2/кремния. Она усиливает свидетельства исследованных
путей обработчиков, оставляя реальное поведение периферии непроверенным.

### Наблюдаемое поведение в этой модели

- Допустимые короткие CRC-запросы, включая невыровненное начало, совпадают со стандартным
  CRC. Пустые, переполняющиеся и выходящие за границы запросы отвергаются. Повтор
  CRC-запроса даёт тот же результат и не меняет выбранный адрес.
- Успешный старт оставляет принятый кадр ожидающим обработки. Вход в резидентный цикл
  повторно обрабатывает его после очистки состояния RAM и формирует дополнительный
  нулевой буфер передачи в этой модели. Незаданный хвост стартового ответа сохраняет
  начальное заполнение RAM. Ни одно поведение не устанавливает точный трафик реальной шины.
- До согласования сессии обычные команды не дают ответа. Завершение сессии снова их
  отключает. Короткий кадр согласования может приниматься, если моделируемые старые
  данные дают оставшийся требуемый байт; обработчик не проверяет моделируемый DLC.
- Полная синтетическая страница из четырёхбайтовых фрагментов достигает модели функции
  flash ровно один раз с ожидаемыми адресом и байтами. Неполная страница не записывается.
  Повторы фрагментов добавляются снова, даже с тем же токеном; дедупликации в проверенном
  пути нет. Потеря ответа поэтому не оправдывает слепого повтора записи.
- Завершение сессии и новое согласование сохраняют счётчик неполной страницы и флаг
  активной страницы. Смена адресного слота не заменяет сохранённый адрес уже активной
  страницы. Повторный вход в инициализацию очищает неполное состояние, но эта операция
  хоста проверки не является командой протокола или доказательством программного сброса.
- Пятибайтовые фрагменты добавляют пять байт, но сдвигают сообщаемый адрес на четыре;
  фрагменты с нулевым количеством тоже его сдвигают. Переполнение буфера, неверные
  адресные слоты, начальное выравнивание страницы и неизвестные команды достигают
  наблюдаемых путей ошибок.
- Запрос стирания диапазона планирует ожидаемые адреса секторов при немедленной
  готовности модели flash. Это не проверяет фактическое завершение стирания или ошибки.

Повторить с подходящим установленным декодером:

```
python tools/check_can_loader_emulation.py IMAGE.bin --report evidence.json
```

Выбрать локальный headless-файл можно через `GHIDRA_HOME` или `--ghidra`. Обёртка
использует рабочие проекты, проверяет финальный маркер успеха и отвергает неисследованные
хеши загрузочной области. В отчёте хеши и явно синтетические векторы модели; полные
логи Ghidra и прошивки локальны. Политика сопоставления ответов и контрпримеры описаны
в [CAN_CLIENT.md](CAN_CLIENT.md).

## Ограничения параллельного доступа к объектам сообщений

Следующие адреса инструкций относятся к I444GI04; проверенный ранний вариант использует
смещение 4. Значения регистров взяты из руководства периферии XC2000,
разделов 20.2.8 и 20.2.12 ([manual](https://www.keil.com/dd/docs/datashts/infineon/xc2000_per_um.pdf)).
Это интерпретация на уровне семейства, а не измерение параллельного доступа на кремнии.

Резидентный цикл читает управление объектом 0 по `0x20101C`, проверяет бит 3 (`NEWDAT`),
вызывает диспетчер и сбрасывает этот бит лишь после возврата обработчика. `RXPND` — бит 0;
проверяется другой флаг. Диспетчер читает данные объекта напрямую несколькими инструкциями,
а не копирует полный запрос в снимок RAM. Исследованный путь не выполняет рекомендованную
руководством последовательность сброса/чтения/повторной проверки `NEWDAT` и `RXUPD`
для подтверждения согласованности принятого кадра.

Новое синтетическое чередование p-code останавливается сразу после сохранения токена
первого запроса адреса, по `0xC0063E`. Замена всего объекта приёма другим полным запросом
адреса и продолжение дают успешный ответ с токеном `0x41`, но выбранный слот становится
`0xC02004` из подменяющего запроса с токеном `0x42`. Исходный запрошенный адрес —
`0xC02000`. Это показывает чувствительность к обновлению объекта на выбранной границе
инструкций, а не то, что такое совпадение произошло или достижимо на реальной шине.
Обновление задаёт тестовая обвязка; конвейер приёма CAN она не моделирует.
Идентичные повторы адреса не меняют слот, но исполнение прежнего назначения после нового
восстанавливает старый адрес; исследованный путь не устраняет дубликаты.

Передающая функция по `0xC004F2` записывает одни и те же регистры данных объекта 1 для
каждого ответа. Она устанавливает `NEWDAT`, копирует данные, устанавливает `MSGVAL`,
сбрасывает `RTSEL`, устанавливает разрешения и запрос передачи. Ожидания завершения
предыдущей передачи и программной очереди ответов в ней нет. Возврат из функции доказывает
лишь исполнение копирования/запроса. Руководство различает хранилище объекта сообщения
и передающий буфер узла; сами записи не устанавливают, какие ожидающие данные попадут
на шину. Текущая обвязка записывает каждый возврат функции как вектор ответа, а не как
завершённую передачу.

Поэтому уникальные токены сами по себе не устанавливают атомарное потребление запроса.
Будущий транспорт должен исключить наложение разных запросов на повторы в очереди
и обосновать согласованность приёма и видимость передачи. Абстрактный перебор FIFO
не охватывает смешанное чтение кадров. Эти тесты не устанавливают пакетный режим,
гарантию аппаратного FIFO или политику повторов адаптера; см. [CAN_CLIENT.md](CAN_CLIENT.md).

## Исключённые области и граница свидетельств по частоте

[Обследование областей](data/can-loader-regions.csv) содержит длины, хеши и количества
байтов, отличных от `00` или `FF`, без экспорта содержимого. Это статистика файлов,
а не измерение стёртой flash или доказательство назначения области.

| Физический интервал, конец исключён | Ожидаемый размер | Наблюдение по 120 файлам |
|---|---|---|
| `0xC00000` — `0xC02000` | 8192 | Загрузочная область исключена исследованными границами CRC/записи |
| `0xC02000` — `0xC90000` | 581632 | Допустимая область обработчиков |
| `0xC90000` — `0xCC0000` | 196608 | Есть во всех файлах; только 3 содержат байты, отличные от `00`/`FF` |
| `0xCC0000` — `0xCD0000` | 65536 | Есть в 41 файле; 23 содержат байты, отличные от `00`/`FF`; отсутствует в остальных 79 файлах |

Исключения среди хвостов: 3 образа I445GBA2, I475MA02 и I486GS09, в каждом по 4 таких
байта по смещениям файла с `0xBFFF8` до `0xBFFFB`. Их назначение не установлено;
отбрасывать их как заполнение на этом основании нельзя. В I444GI04 средний исключённый
интервал нулевой, а последний массив содержит 16580 байт, отличных от `00`/`FF`.
Прежняя стендовая документация связывает этот массив с эмулируемой EEPROM; обследование
файлов независимо не устанавливает её поведение при исполнении или идентичность донора.
Отсутствие байтов в коротком файле не означает стёртую или отсутствующую память устройства.

Повторить: `tools/survey_can_loader.py DIR --regions-csv regions.csv`. Адресная карта
применяется только к исследованным отпечаткам загрузчика. Чтение допустимой области
по CAN поэтому всё ещё дало бы частичный образ; CAN-писатель должен сохранять или
отдельно учитывать исключённые области и требование полного бэкапа.

Результат по частоте остаётся условным. Исследованная настройка загрузчика задаёт PLL
и делители CAN, но не устанавливает унаследованное состояние мультиплексора системной
частоты. Доступный образ flash не содержит реализации сброса масочного ROM. Проверка
исполнения обработчиков намеренно начинается после этой настройки и не может разрешить
вопрос. Подтверждение 500 кбит/с всё ещё требует точных свидетельств стартового состояния
модификации или последующего измерения; модель с заданной частотой лишь предположила бы ответ.

Экспериментальное исполнение инициализации тактирования не подтвердило этот путь:
модели не хватило семантики регистров тактирования и статуса, затем был исчерпан бюджет
инструкций в цикле ожидания. Это ограничение модели, а не наблюдаемое зависание ЭБУ.
Экспериментальное расширение не включено в проверенный скрипт обработчиков и не даёт
дополнительного подтверждения скорости CAN.
